# 029 プロジェクトのデプロイの合図は `release` ブランチへの push。版の名前は、そのコミットのタグ。基盤のコードはタグで版を決める

- 決めた日: 2026-11-19

## 背景

ADR 015 で、次の 2 つを決めた。

- プロジェクトのリポジトリにタグ（例: `v1.2.3`）を push すると、そのプロジェクトをビルドしてデプロイする。
- 基盤のコードも、タグで版を決めて VM に届ける。

この ADR は、ADR 015 を置き換える。1 つ目を変え、2 つ目はそのまま引き継ぐ。

OCI DevOps の GitHub のトリガーは、タグの push からビルドできない（[references/oci-devops.md](../references/oci-devops.md) §3）。

- トリガーの絞り（`headRef`）は、文書では push のブランチの名前とされる。タグやワイルドカードの記述は無く、公開の例も見つからなかった。
- 絞りがタグに合ってビルドが始まっても、DevOps はタグの ref（`refs/tags/<名前>`）をブランチの名前として取りに行き、ソースの取得で失敗する。ビルドの手順（`build_spec.yaml`）に入る前なので、手順では避けられない。

ブランチの push なら、DevOps はそのブランチを取り、取ったリポジトリにはそのコミットのタグも入っている。

ADR 024・026 にある「タグの push」は、この ADR からは `release` への push と読む。

## 決定

- プロジェクトのリポジトリの `release` ブランチへの push で、そのプロジェクトをビルドしてデプロイする。トリガーの絞りは基盤で固定する。
- デプロイする版の名前（`AFP_TAG`）は、`release` の先頭のコミットに付いた `v` で始まるタグの名前。そのようなタグが無い、または複数あるときは、ビルドを失敗にする（成否のメールで分かる）。
- プロジェクトは、タグを打ってから、`release` とタグを 1 回の push で送る（`git push --atomic origin HEAD:release <タグ>`）。
- ビルドのパイプラインのソースの既定のブランチも `release` にする（手で始めたビルドが取るブランチ）。
- 作ってあるトリガーの絞りが違えば、`make apply` が、トリガーを作り直さずに絞りだけを直す（トリガーの URL と webhook の Secret は変わらない）。
- 基盤のコードは、タグで版を決めて VM に届ける（ADR 015 から引き継ぐ）。どのタグを使うかを Object Storage に置き、VM の `afp` はそのタグのコードを公開リポジトリから取って入れ替える。

## 理由

- タグの push からはビルドできず、ブランチの push ならできる。基盤の外の仕組みを足さずに済む。
- デプロイの合図を、ふだんの push と分けて明示的にする。`main` への push のたびにデプロイすると、手元で確かめる前に本番に届く（ADR 015 の理由のまま）。
- 版の名前をタグで付ければ、本番に出した版に名前が付き、どのコミットかが後から分かる。戻すときも版の名前で指せる（ADR 015 の理由のまま）。ADR 015 がブランチへの push を退けた理由（出した版に名前が残らない）は、版の名前をタグで付けるので当たらない。
- タグが複数あると、どれを版にするかが並べ方で決まり、意図しない版を出しうる。失敗にすれば気付ける。
- 別々に push すると、タグが届く前にビルドがソースを取り、版の名前が見つからないおそれがある（未確認）。1 回の push なら、その心配が減る。
- 基盤のコードの版を VM の作成時の設定（user_data）に入れると、版を上げるたびに VM が作り直される。Object Storage に置けば、VM を作り直さずに上げられる（ADR 015 の理由のまま）。

## 採らなかった案

| 案 | 理由 |
|---|---|
| プロジェクトのタグの push でデプロイする（ADR 015） | OCI DevOps のトリガーでは、タグの push からビルドできない |
| `main` への push でビルドし、タグがあるときだけ進める | タグを先に push しないと、その版を見送る。`main` への push のたびにビルドの実行環境を借りる |
| タグを使わず、`release` に push したコミットの短い SHA を版の名前にする | 出す手順は 1 つで済むが、版の名前が読みにくい |
| GitHub Actions や Functions でタグの push を受け、ビルドを API で始める | OCI の外の仕組みと認証が増える |
| タグが複数あるとき、並べた先頭を選ぶ | `v10` と `v9` のように、並べ方で意図しない版を選びうる |
| 基盤のコードを、手元の HEAD の tar として Object Storage に置く | GitHub への push とタグ打ちが要らず開発中は速いが、版の管理がタグほどはっきりしない（ADR 015 の理由のまま） |

## 引き換え

- 出す手順が、タグを打つことと、`release` との push の 2 つになる。
- タグを付けずに `release` だけを push すると、ビルドが失敗する。タグをあとから送っても、ビルドはやり直されない（手でビルドを始め直す。手で始めたビルドが同じに動くかは未確認）。
