# 040 NLB を入口にし、サブネットを役目ごとに分ける

- 決めた日: 2026-11-25

## 背景

VM はパブリック・サブネットにあり、予約済みの公開 IP を付けて、80 番と 443 番を外から直接受けていた。DB はプライベート・サブネットにあった。Bastion の口は DB のサブネットに置き、そこから VM の 22 番にも届くよう、DB のセキュリティ・リストに VM 向けの規則を足していた。

VM が外から届く場所にあり、DB のセキュリティ・リストに DB と関係の無い規則が混ざっていた。一般的な形（入口だけを外に出し、ほかはプライベートに置く）に近づけたほうが、規則が役目どおりに読め、かえってわかりやすいと考えた。

## 決定

- VCN のサブネットを、役目ごとに 4 つに分ける。
  - パブリック: NLB だけ。
  - VM 用（プライベート）: VM。公開 IP を持たない。外へは NAT ゲートウェイ、OCI のサービスへはサービス・ゲートウェイから出る。
  - DB 用（プライベート）: HeatWave。今のサブネットをそのまま使う。
  - Bastion 用（プライベート）: Bastion の口。VM の 22 番と DB の 3306 番にだけ出られる。
- 入口は、公開の NLB（[references/oci-network-load-balancer.md](../references/oci-network-load-balancer.md)）。TCP の 80 番と 443 番を、VM の同じ番号へそのまま通す。証明書の取得とドメイン名での振り分けは、今までどおり Caddy が行う。
- 送信元 IP を保持する（OCI の既定）。443 番を `home_cidrs` に絞るのは、パブリック・サブネットのセキュリティ・リストで行う。VM は 80 番と 443 番を全体から許す（利用者の IP のまま届くため）。VM には公開 IP が無いので、NLB を通らずには届かない。
- NLB の IP は予約しない。DNS の A レコードは、本体のスタックが NLB の IP に向ける。VM の予約済みの公開 IP は無くす。
- ヘルスチェックは TCP（その番号に接続できるか）。

## 理由

- 外に出るのが NLB だけになり、ほかの部品はプライベートに置ける。
- セキュリティ・リストを役目ごとに持てる。DB のセキュリティ・リストは DB の規則だけになる。
- NLB は L4 なので、Caddy の作り（証明書の取得・振り分け）を変えずに済む。NLB は Always Free に入っていて、費用は増えない見込み（[references/oci-free-tier.md](../references/oci-free-tier.md)）。
- NLB の IP は、VM を作り直しても変わらない。NLB を作り直せば変わるが、レコードは本体が直すので、予約する理由が無い。
- VM が NAT ゲートウェイから外へ出るので、VM を作った直後から外へ出られる（予約済みの IP が付くまで出られない、ということが無くなる。[references/oci-compute-vm.md](../references/oci-compute-vm.md)）。
- TCP のヘルスチェックなら、Caddy のドメイン名での振り分けに合わせた設定が要らない。

## 採らなかった案

| 案 | 理由 |
|---|---|
| 今のまま（VM をパブリック・サブネットに置く） | VM が外から届く場所に残り、規則が役目どおりに分かれない |
| L7 のロードバランサー | TLS を解くので、証明書を Caddy から移すか、二重に持つことになる。Always Free は 1 台・10 Mbps |
| サブネットを 3 つにし、Bastion の口を DB 用に置く | DB のセキュリティ・リストに、VM の ssh のための規則が混ざる |
| Bastion の口を VM 用に置く | VM のセキュリティ・リスト（80・443 番を全体から許す）が口にも掛かる |
| 送信元 IP を保持しない | VM の規則は「パブリック・サブネットから」に絞れて素直になるが、アプリから利用者の IP が見えなくなる。OCI の既定を変える理由が無い |
| NLB の IP を予約する | 資源が増えるだけで、DNS は本体が直すので要らない |

## 引き換え

- 送信元 IP を保持するとき、VM の返事がどう利用者に返るかは、公式文書に書かれていない。返らなければ、保持しない形に切り替える。
