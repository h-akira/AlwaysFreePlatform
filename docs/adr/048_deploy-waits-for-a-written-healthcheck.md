# 048 デプロイは、healthcheck が書いてあれば healthy になるまで待つ

- 決めた日: 2026-11-28

## 背景

ADR 036 は、「デプロイは起動できたら成功とし、healthcheck を待たず、見ない」と決めた。そのため、アプリが起動してすぐ落ちても、デプロイは成功と報告されていた。また、プロジェクトが compose に healthcheck を書いても、基盤はそれを無視していた。

人が望んでいたのは、healthcheck を必須にしないことで、書いてあるときまで無視することではなかった。

この ADR は、ADR 036 のうち、待たないことと healthcheck を見ないことだけを改める。自動では戻さないこと、今のバージョンの記録を起動の前に変えることは、ADR 036 のまま。

## 決定

- `afp deploy`（`make rollback` を含む）は、`docker compose up -d --no-build --remove-orphans --wait --wait-timeout 300` でコンテナを起動する。
  - healthcheck を書いたコンテナは、healthy になるまで待つ。unhealthy になるか、300 秒を過ぎたら、デプロイは失敗。
  - healthcheck を書いていないコンテナは、起動（running）したら成功。
- healthcheck は、今までどおり任意。
- 失敗しても、前のバージョンへ自動では戻さない。新しいバージョンのコンテナはそのまま残る。
- 待つのはデプロイのときだけ。VM の再起動のあとの起動（`afp sync`）は待たない。1 つのプロジェクトが healthy にならなくても、Caddy とほかのプロジェクトを止めないため。
- 基盤が想定するコンテナは、起動したら動き続けるもの（起動のときにマイグレーションなどのコマンドを流すのはよい）。1 回だけ動いて終わるコンテナは想定しない。

## 理由

- healthcheck を書いたプロジェクトは、デプロイが失敗したことを、そのとき通知で知れる。書かないプロジェクトは、今と変わらない。
- 自分で待つ仕組みを `afp` に書かず、Compose の `--wait` を使えば、変えるのはコマンドの 1 行で済む。
- ローカルの Docker（Compose v2.32.4）で試し、Compose のソースも読んで、`--wait` が上のとおりに動くことを確かめた。
  - healthcheck を書いたコンテナは、healthy で成功、unhealthy・時間切れで失敗になった。
  - healthcheck を書いていないコンテナは、running で成功になった。
  - 失敗しても、新しいコンテナは止められずに残った。
- 1 回だけ動いて終わるコンテナは、ほかのコンテナから待たれていないと、確かめた瞬間の状態で成否が決まった（すぐ exit 0 で終わると失敗、1 秒後に exit 1 で終わると成功）。基盤はこの形を想定しないので、問題にしない。
- 300 秒は、ADR 033 で待っていた時間と同じ。自動のデプロイの手順のタイムアウト（1800 秒）と、`make` の Run Command のタイムアウト（3600 秒）に収まる。

## 採らなかった案

| 案 | 理由 |
|---|---|
| 今のまま、待たない（ADR 036） | 書いた healthcheck を基盤が無視する |
| `afp` が、healthcheck を書いたコンテナだけを自分で見て待つ | 1 回だけ動いて終わるコンテナを想定しないなら、`--wait` で足りる。コードが数十行増える |
| 待って、失敗したら前のバージョンへ戻す（ADR 033） | ADR 036 の理由のとおり（新しいバージョンが DB を変えていると、前のバージョンが動かないことがある） |

## 引き換え

- healthcheck を書いていないコンテナが、起動したあとで落ちても、デプロイは成功になる（今と同じ）。
- 起動の直後に落ちるコンテナでも、`restart` の設定があると、`--wait` は running の瞬間を見て成功にすることがある。確実に知りたいプロジェクトは healthcheck を書く。
- healthcheck を書いたプロジェクトでは、デプロイが最大 300 秒長くなる。
