# 045 バケットを役目ごとに 3 つに分ける

- 決めた日: 2026-11-26

## 背景

基盤のバケットは `bucket-afp-main` の 1 つで、次のものが全部入っていた。

- 基盤を動かす物: どのプロジェクトをどう動かすか（`afp.json`。Terraform が書く）、各プロジェクトの今の版（`state/`）、リリース一式（`releases/`。ADR 022）、基盤のコード（`platform.tar.gz`）
- DB のダンプ（`dumps/`）
- `afp` の操作のログ（`logs/`。`afp` の操作 1 回で 1 ファイル。Run Command が手元に返すのは出力の最後の 1 KB だけなので、全部の出力を置く）

ダンプを 28 日で消すと決めた（ADR 042）。操作のログも、消すまで残っていた。

## 決定

- バケットを 3 つにする。`bucket-afp-main` は無くす。

| バケット | 中身 | 消す規則 |
|---|---|---|
| `bucket-afp-deploy` | `afp.json`・`state/`・`releases/`・`platform.tar.gz` | 無し |
| `bucket-afp-dumps` | DB のダンプ（`<プロジェクト>/<UTC の時刻>[-before-<版のタグ>].sql.gz`） | ライフサイクル・ポリシーで 28 日 |
| `bucket-afp-logs` | `afp` の操作のログ（`<UTC の時刻>-<操作>[-<プロジェクト>].log`） | ライフサイクル・ポリシーで 28 日 |

- VM は、`bucket-afp-deploy` を読み書きできる。`bucket-afp-dumps`・`bucket-afp-logs` には、新しく置くことだけができる（読む・消す・上書きはできない。権限の絞り方が効くかは未確認）。
- ライフサイクル・ポリシーを Object Storage が実行するための権限（Object Storage のサービスへのポリシー）を、本体のスタックに置く。
- 名前は `bucket-afp-<役目>`（ADR 031）。

## 理由

- 中身ごとに、消す規則・権限・大事さが違う。バケットで分ければ、消す規則はバケット全体に 1 つで済み、名前で絞る必要が無い。
- VM の権限をバケットで絞れる。ダンプ（全プロジェクトのデータ）とログを、VM が読んだり消したりできなくなる。
- 費用は変わらない（保存の量で決まり、バケットの数では決まらない）。

## 採らなかった案

| 案 | 理由 |
|---|---|
| 1 つのバケットのまま、名前の頭（`dumps/`・`logs/`）ごとに消す規則を書く | 権限をバケットで分けられない。基盤を動かす物と、消えてよい物が混ざる |
| ダンプのバケットだけを分け、ほかは `bucket-afp-main` に残す | 操作のログも消す規則が要り、基盤を動かす物と混ざるのは変わらない |
| `bucket-afp-main` の名前を残す | 中身が「VM で何をどの版で動かすか」の物だけになり、名前で役目が分かるほうがよい |

## 引き換え

- バケットの名前を変えると、バケットは作り直しになる（中身は `make apply`・`make platform`・各プロジェクトのデプロイのし直しで作り直せる）。古いバケットにあったダンプとログは引き継がない。
- VM は、置いたダンプとログを自分で読めない。読むのは手元（管理者の権限）から行う。
