# 036 デプロイは起動できたら成功とし、待たず、自動では戻さない

- 決めた日: 2026-11-23

## 背景

ADR 033 で、compose の `healthcheck` を任意にした。そのうえで、デプロイは全サービスが動くのを待ち（`healthcheck` を書いたサービスはヘルスチェックに通るのを最大 5 分）、待ち終わらなければ前の版に戻していた（前の版が無ければ止めていた）。

待つことと自動で戻すことは、どちらも基盤がプロジェクトの中身の正しさに踏み込む仕組みで、そのぶん `afp` も約束も複雑になる。

この ADR は ADR 033 を置き換える。

## 決定

- `afp deploy` は、イメージを取ってコンテナを起動する（`docker compose up -d`）だけにする。起動できたら成功とする。ヘルスチェックを待たない。
- 起動できなかったときは、失敗として知らせる（`afp deploy` がエラーで終わる。自動のデプロイなら失敗のメールが届く）だけにし、前の版には戻さない。
- 今の版の記録は、起動する前に、デプロイする版にする。起動できなくても、記録はその版のまま（前の版は、その前に動いていた版）。
- 前の版に戻すかどうかは人が決め、戻すなら `make rollback` を使う。
- デプロイの直前の DB のダンプは、今のまま取る。
- 基盤は `healthcheck` を見ない。書くかどうかと、その使い方はプロジェクトが決める。

## 理由

- シンプルさを優先する。アプリが正しく動いているかはプロジェクトの責任で、基盤はコンテナを起動するところまでを受け持つ。
- 自動の戻しは、新しい版が DB を変えていると、戻した前の版がその DB で動かないことがある。戻すかどうかは、事情を知る人が決めるほうがよい。
- 待たなければ、`afp` から待つ時間と戻しの分岐が無くなり、デプロイの結果が単純になる（起動できたか、できなかったか）。
- 記録をいつもデプロイした版にすれば、記録と動いているものが一致する。失敗したあとに `make rollback` を流せば、失敗する前に動いていた版に戻る。起動できたときだけ記録すると、失敗したあとの `make rollback` が、さらに 1 つ前の版を出してしまう。

## 採らなかった案

| 案 | 理由 |
|---|---|
| 今のまま、待って、待ち終わらなければ戻す（ADR 033） | 基盤がアプリの正しさに踏み込み、仕組みが増える |
| 待って成否を知らせるが、戻さない | 待つ仕組みが残る。`healthcheck` の意味を基盤が決めることになる |

## 引き換え

- 起動したあとでアプリが正しく動かなくても、デプロイは成功になる。気付くのは、各プロジェクトのアプリの監視。
- 失敗したデプロイのあとは、新しい版のコンテナがそのまま残る（動いていないこともある）。VM を再起動したり作り直したりしても、記録どおり新しい版で起動する。
