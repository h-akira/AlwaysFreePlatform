# 03 役割と責任

[01](01_purpose.md) §4 の方針どおり、基盤の管理者とプロジェクトの管理者の受け持ちを分ける。ここで決めた境目が、基盤とプロジェクトの約束になる。

## 1. 二つの役割

| 役割 | 受け持つもの |
|---|---|
| **基盤の管理者**（以下「基盤」） | 共有のもの。VM・入口（Caddy・証明書・DNS）・MySQL HeatWave の DB システム・Vault の仕組み・DevOps の共通部分・Object Storage・レジストリ・ネットワーク・IAM・費用（[02](02_architecture.md) §3） |
| **プロジェクトの管理者**（以下「プロジェクト」） | 自分のプロジェクトの中のもの。アプリ・自分の DB の中身・自分のシークレットの値・自分のアプリの監視 |

[01](01_purpose.md) §4 のとおり、二つの役割はほぼ同じ人が担うことを前提にする。OCI の中の操作（ローカルからのデプロイ・シークレットの値を入れること・ログを見ること・VM や DB に入ること）は基盤の管理者が行い、基盤はプロジェクトの管理者ごとの OCI の権限もログの読み分けも用意しない。アプリのログは全プロジェクトで 1 つのログにまとまる（[02](02_architecture.md) §5.11）。違う人のプロジェクトを同居させることは、まず無理と考える。

それでも受け持ちは分け、ここで決めた境目を約束として扱う。

原則: **基盤は仕組みを用意し、プロジェクトはそれを使う。基盤はプロジェクトの中身（アプリの正しさ・データ）に責任を持たない。プロジェクトは共有のものを直接触らない。**

## 2. 責任の表

| 対象 | 基盤 | プロジェクト |
|---|---|---|
| VM（作成・作り直し・OS の更新） | ◎ | — |
| 入口（Caddy・証明書・振り分け） | ◎ | — |
| 443 を公開するか（全体に開くか、決めた IP からだけか） | ◎ 切り替える（入口で一律。80 は常に開ける。[02](02_architecture.md) §5.4） | 公開が要るかを基盤に伝える。公開されたときは自分のログインで守る |
| ドメインと DNS | ◎ ゾーンを持ち、プロジェクトの名前から払い出す（`<名前>.<ゾーン>`）。レコードを VM の IP に向ける | — |
| ビルドとデプロイの仕組み（DevOps の共通部分・`afp deploy`・成否の通知） | ◎ | 約束のファイルを書く。自動のデプロイを使うなら、バージョンのタグを付けて自分のリポジトリの `release` に push する。使わないなら、デプロイを基盤の管理者に頼む |
| アプリの動作・不具合 | — | ◎ |
| 失敗したデプロイのあと、前のバージョンに戻すか | ツール（`make rollback`）を用意し、実行する | ◎ 戻すかどうかを決める |
| ログインと、その回数制限 | — | ◎ アプリの中で行う。基盤の入口は持たない |
| HeatWave の DB システム（稼働・定期的に触ること・接続数の全体の上限） | ◎ | — |
| プロジェクトの DB とユーザの作成 | ◎ | — |
| DB の中身（テーブル・マイグレーション・データの正しさ） | — | ◎ |
| MySQL のバージョンが上がったとき | ローカル用のバージョンの指定を上げ、通知する | 自分のアプリをテストし直す |
| DB のバックアップ（週 1 回のダンプ・デプロイの直前のダンプ。28 日で消える。[02](02_architecture.md) §5.3） | ◎ 仕組みを動かす。失敗のメールを受けて対処する | — |
| DB の復元 | ツール（DB へのトンネル）を用意し、実行する | 戻すかどうか・どの時点に戻すかを決める |
| シークレットの仕組み（Vault・名前の決まり・環境変数への差し込み） | ◎ | — |
| シークレットの値 | 生成できるものは基盤が生成する。外から持ってくる値は、基盤の管理者が Vault に手で作る | 外から持ってくる値（外部の API キーなど）を基盤の管理者に渡す |
| アプリのログを VM の外に残すこと（OCI Logging に 30 日） | ◎ 仕組みを動かし、頼まれたらログを見る | ログを標準出力・標準エラーに出す。秘密の情報を出さない |
| 基盤の監視（外から VM に届くか、HeatWave が動いているか、VM のメモリとディスク） | ◎ | — |
| アプリの監視（自分のアプリが使えるか） | — | ◎ 基盤はツールもサンプルも用意しない |
| 費用 | ◎ 予算とアラート | メモリの上限などの約束を守る |

- VM や Caddy が止まったことは、基盤の監視で分かる。証明書が切れたことや、アプリが正しく答えないことは分からない。各プロジェクトのアプリの監視で気付く。
- 基盤の操作（デプロイ・DB の削除・復元）を Web で受け付けることはしない。基盤の操作は、基盤の管理者がローカルから OCI の仕組み（Run Command・Bastion）を通して行う。

## 3. 境目

基盤とプロジェクトがやり取りするのは、次のものだけ。

| 向き | もの |
|---|---|
| プロジェクト → 基盤 | プロジェクトの一覧の1項目（名前・リポジトリ（任意）・ポート（任意）・デプロイする VM・設定値・シークレットの名前と作り方）。基盤の非公開の設定に書く |
| プロジェクト → 基盤 | 約束のファイル（コンテナの構成。自動のデプロイを使うなら、ビルドの手順も）。プロジェクトのリポジトリに置く |
| プロジェクト → 基盤 | 自動のデプロイを使うときは、自分のリポジトリの `release` への push（そのコミットに付けた `v` で始まるタグの名前が、デプロイするバージョン名になる） |
| 基盤 → プロジェクト | プロジェクトのドメイン（名前から決まる）と、443 を公開しているか |
| 基盤 → プロジェクト | 値（DB の接続先・ドメイン・プロジェクト名・設定値・シークレット）。デプロイのたびに、約束のファイルの変数として渡す |
| 基盤 → プロジェクト | 本番の MySQL のバージョンと設定（ローカルの開発用）。基盤のリポジトリに置く |
| 基盤 → プロジェクト | デプロイの成否、MySQL のバージョンが上がったことの通知 |
| 基盤 → プロジェクト | アプリのログ（コンテナの標準出力と標準エラー）。OCI Logging に送る |
| 基盤 → プロジェクト | ツール（ローカルからのデプロイ・ロールバック・DB へのトンネル）。基盤のリポジトリに置く |
