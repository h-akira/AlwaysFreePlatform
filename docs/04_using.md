# 04 基盤を使う

プロジェクトの管理者向け。基盤にプロジェクトをデプロイするために守る約束と、共有の DB を使うときの注意を書く。

約束は、コンテナを動かしてもらうのに要る最小限だけにしてある（[01](01_purpose.md) §4）。ここに書いていないこと（言語・フレームワーク・コンテナの数と構成・ローカルの開発環境・テスト・アプリの監視）は、プロジェクトが自由に決める。

## 1. 基盤に伝えること

プロジェクトを基盤に加えるときは、基盤の管理者に次を伝え、プロジェクトの一覧に1項目足してもらう（[03](03_responsibilities.md) §3）。

| 項目 | 内容 |
|---|---|
| 名前 | プロジェクトの名前。英小文字・数字・ハイフン。ドメイン（`<名前>.<基盤のゾーン>`）・DB・シークレット・ネットワーク・エイリアスなど、基盤の中の名前はすべてこれから作る。名前を変えるとドメインも変わる |
| リポジトリ | GitHub のリポジトリ。非公開でもよい。伝えると、`release` ブランチへの push でビルドとデプロイが動く。伝えなければ、デプロイは基盤の管理者がローカルから行う |
| ポート | 外から受けるサービスが HTTP を待ち受けるポート。省けば 8080 |
| デプロイする VM | どの VM にデプロイするか |
| 設定値・シークレット | アプリに渡す値の名前と、その種類（下の表）。名前は英大文字で始め、英大文字・数字・`_` だけを使う。`AFP_` で始まる名前は基盤が使うので付けない。1 つの名前は 1 つの種類にだけ書く |

| 種類 | 意味 |
|---|---|
| 設定値 | 秘密でない値。値をそのまま伝え、基盤の非公開の設定に書いてもらう（例: `EXAMPLE_SETTING`） |
| 生成するシークレット | 基盤が値を生成する。人は値を見なくてよい（例: `EXAMPLE_SIGNING_KEY` のような署名鍵） |
| 手で作るシークレット | 外から持ってくる秘密の値。値を基盤の管理者に渡し、管理者が Vault に手で作る（例: `EXAMPLE_API_KEY` のような外部の API キー） |

- DB のパスワードは、書かなくても基盤が必ず作る。英字・数字・記号で作り、記号を必ず含める。接続の URL に埋め込むなら、プロジェクトがエスケープする。

## 2. プロジェクトのリポジトリに置くもの

プロジェクトのリポジトリに **`compose.afp.yaml`**（Docker Compose の形式）を置く。基盤はこれを使ってイメージをビルドし、コンテナを動かす。守ることは次のとおり。

1. **外から受けるサービスを1つ決める**。そのサービスを `afp` ネットワーク（基盤が用意する外部のネットワーク）に、**プロジェクトの名前をエイリアスにして** 参加させ、§1 で伝えたポート（省けば 8080）で HTTP を待ち受ける。HTTPS は基盤の入口が受けるので、アプリは HTTP だけでよい。
   - **`afp` に入れるのは、このサービスだけ** にする。`afp` には全プロジェクトの要求を受けるサービスが集まり、サービスの名前（`web`・`redis` など）がぶつかると、別のプロジェクトのコンテナにつながりうる。
   - DB は VM の外にあるので、`afp` に入れなくても、どのサービスからも §3 の値で接続できる。
2. **自分で作るイメージは、`build:` と `image: ${AFP_IMAGE_PREFIX}/<名前>:${AFP_TAG}` を書く**。基盤は `build:` のあるサービスだけを、VM の CPU の種類向けにビルドして、その名前で OCIR に置く。`build:` のサービスが 1 つも無ければ、デプロイを断る。`build:` の無いサービスは、公開のイメージをそのまま pull する。
3. **デプロイは、`healthcheck` を書いたコンテナが healthy になったら成功**。書いていないコンテナは、起動できたら成功（書くかどうかは自由）。unhealthy になるか 5 分を過ぎたら、失敗として通知するだけで、前のバージョンには戻さない（[ADR 048](adr/048_deploy-waits-for-a-written-healthcheck.md)）。コンテナは、起動したら動き続けるもの（起動のときにコマンドを流すのはよい）。起動したあとでアプリが正しく動き続けるかは、プロジェクトが確かめる。
4. **各サービスに `mem_limit` を書く**。
5. **環境で変わる値は、すべて環境変数で受ける**。ドメインもパスワードもファイルに書かない。だから `compose.afp.yaml` は公開してもよい。

最小の形は次のとおり。

```yaml
services:
  web:
    build: .
    image: ${AFP_IMAGE_PREFIX}/web:${AFP_TAG}
    environment:
      AFP_DB_HOST: ${AFP_DB_HOST}
      AFP_DB_PORT: ${AFP_DB_PORT}
      AFP_DB_NAME: ${AFP_DB_NAME}
      AFP_DB_USER: ${AFP_DB_USER}
      AFP_DB_PASSWORD: ${AFP_DB_PASSWORD}
      EXAMPLE_SIGNING_KEY: ${EXAMPLE_SIGNING_KEY}
      BASE_URL: https://${AFP_DOMAIN}
    mem_limit: 128m
    networks:
      afp:
        aliases: ["${AFP_PROJECT}"]
networks:
  afp:
    external: true
```

- `AFP_TAG` は、デプロイするバージョン名（自動のデプロイではバージョンのタグの名前、ローカルからのデプロイでは時刻か指定した名前。02 §5.6）。
- リポジトリを基盤に伝えたプロジェクトは、さらに **`build_spec.yaml`**（OCI DevOps のビルドの手順）を、リポジトリの一番上に置く。基盤のリポジトリの `examples/hello/build_spec.yaml` をコピーし、`AFP_TAG` の指定と「release with the platform」の手順は変えない。その前に、自分の手順（テストなど）を足してよい。
  - 出すときは、コミットに `v` で始まるタグを 1 つ付け、`release` ブランチとタグを 1 回の push で送る（例: `git push --atomic origin HEAD:release v1.2.3`）。`release` への push で、ビルドとデプロイが動く。ビルドは基盤の VM の上で行われる。
  - タグが無い・複数あるときにデプロイしないことは、02 §5.6 のとおり（失敗のメールが届く）。タグをあとから送っても、やり直されない。`release` とタグを別々に送ると、タグが届く前にビルドが始まり、同じことが起きるおそれがある（未確認）。
  - 前のデプロイが終わる（成否のメールが届く）まで、次を出さない。続けて出すと、どちらのバージョンが本番に残るかは決まらない（後から push したほうとは限らない）。
- リポジトリを伝えないプロジェクトは、基盤の管理者がローカルからデプロイする（`make deploy`）。
- 動くサンプルは、基盤のリポジトリの `examples/hello` に置く。

## 3. 基盤が渡す値

デプロイのたびに、基盤は次の値を、`docker compose` を動かすときの変数として渡す。`compose.afp.yaml` の中で `${変数}` として使える。コンテナの中で使うには、§2 の例のように `environment` に書いて渡す。

| 変数 | 中身 |
|---|---|
| `AFP_IMAGE_PREFIX` | イメージの保存先。OCIR の、このプロジェクト用の名前のプレフィックス（例: `iad.ocir.io/<namespace>/repo-afp-app-a`） |
| `AFP_TAG` | デプロイするバージョン名 |
| `AFP_PROJECT` | プロジェクトの名前 |
| `AFP_DOMAIN` | プロジェクトのドメイン（`<名前>.<基盤のゾーン>`） |
| `AFP_DB_HOST`・`AFP_DB_PORT` | DB の接続先 |
| `AFP_DB_NAME`・`AFP_DB_USER`・`AFP_DB_PASSWORD` | プロジェクトのデータベース・ユーザ・パスワード |
| 設定値・シークレットの名前（例: `EXAMPLE_SIGNING_KEY`） | §1 で伝えた設定値・シークレットの値 |

## 4. そのほかの約束

- **マイグレーションはアプリが行う**（起動時など）。基盤はデプロイの直前に DB のダンプを取るだけで、マイグレーションには関わらない。
- **前のバージョンに戻しても、DB は戻らない**。ロールバック（`make rollback`。基盤は自動では戻さない）が戻すのは、イメージと `compose.afp.yaml` だけ。新しいバージョンが DB を変えたなら、前のバージョンがその DB で動くようにしておく（列を消す・名前を変えるといった変更は、バージョンを分けて行う）。基盤はデプロイの直前ごとと、週 1 回、ダンプを取る。ダンプは 28 日で消えるので、それより前の時点には戻せない（[02](02_architecture.md) §5.3）。DB を戻すかどうかと、どの時点に戻すかは、プロジェクトが決める（[03](03_responsibilities.md) §2）。
- **DB への接続の数を小さくする**（接続プールで数本）。DB の接続の上限は、全プロジェクトで共有している。
- **ログは標準出力・標準エラーに出す**。基盤がそれを OCI Logging に送り、30 日残す（[02](02_architecture.md) §5.11）。ファイルに書いたログは送られず、VM を作り直すと消える。ログは全プロジェクトで 1 つのログにまとまり、ログを読める人には全プロジェクトのログが見えるので、**秘密の情報（パスワード・トークン・個人情報）をログに出さない**。1 行 1 件の JSON にすると検索しやすい（任意）。
- **VM の中にファイルを残さない**。VM はいつ作り直されてもよいようにしてある（[02](02_architecture.md) §4）。アプリが受け取ったファイルを残すなら、プロジェクトが自分で Object Storage などに置く。
- **イメージは、amd64 と arm64 のどちらでもビルドできるように作る**。基盤の VM の CPU の種類は、取れる VM によって替わる（[02](02_architecture.md) §5.2）。基盤は、そのときの VM の CPU の種類向けにビルドする。
- **DB の文字コードは `utf8mb4`、既定の照合順序は `utf8mb4_ja_0900_as_cs_ks`**。基盤はこれを既定にしてデータベースを作る。テーブルや列ごとに替えるのはプロジェクトの自由。
  - 濁点・半濁点・ひらがなとカタカナ・大文字と小文字・小書きの文字（「ゃ」と「や」）を区別し、全角と半角だけを同じとみなす。並び順は日本語の順。
  - 照合順序ごとの違いは [references/mysql-notes.md](references/mysql-notes.md) §2。
- **ローカルの開発では、基盤のリポジトリの `mysql/VERSION` のバージョンの公式の `mysql` のイメージに、`mysql/heatwave.cnf` を読ませる**。本番と振る舞いが変わる設定（`partial_revokes`・タイムゾーン・既定の照合順序など）を揃えてある。

MySQL でアプリを書くときに、ほかの DB との違いで気を付けることは [references/mysql-notes.md](references/mysql-notes.md) にまとめてある。
